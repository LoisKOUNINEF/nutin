# Methodology

## Why full combinatorial, not sampling

Feature-wiring bugs in this codebase have repeatedly come from a single flag name or relative path drifting out of sync between two files — a context key set in `lib/src/*` but never checked by a `.hbs` conditional, two different typos for the same flag in two different templates, a feature folder's internal path not mirroring its output path. These bugs are invisible unless the exact combination that exercises both sides of the drift is generated and built. Sampling a few representative combos has historically missed real, shipped bugs; running every combination has caught them. See `packages/nutin/CHANGELOG.md` and git history for concrete precedent.

## Verify empirically, never by code reading alone

A `.hbs` file that *looks* correct can still fail once actually rendered and built — Handlebars conditionals reference context keys that may not exist, imports reference paths that may not resolve once templates land in a real project structure, generated `package.json` scripts may reference tools that were never added as dependencies. For every cell in the matrix: generate a real scratch app, run the real script, inspect real output (`dist/`, exit codes, actual file contents) — not just the source template.

## Fix-as-you-go

When a cell fails:
1. Diagnose root cause in `packages/nutin/lib/src/*` or `packages/nutin/templates/*` — never patch the generated scratch app itself, that's not where the fix belongs.
2. Apply the minimal fix.
3. Re-run just that cell to confirm, then continue the sweep — no need to restart dimensions already passed.
4. A cell "failing" isn't automatically a bug — confirm it isn't expected/guarded behavior (e.g. the `tailwind` toggle correctly refusing to build without its devDeps installed, see `MATRIX.md`) or a mistake in your own test invocation before treating it as a real defect.

## Scope

`packages/nutin/templates/` and `packages/nutin/lib/` only. Don't use `apps/website` or `apps/tutorial` as a reference for "correct" nutin behavior — they're separately maintained consumer projects that may have drifted from the current templates; they're downstream of this package, not a source of truth for it.

Don't inject content into `README.md` or other prose docs as a side effect of a test pass. Config files (`nutin.config.js`) are meant to be hand-edited and are fair game for the config-toggle dimension.

When diffing two generated app trees for structural equivalence, exclude `node_modules/`, `.git/`, `dist*/`, `.nutin-meta.json`, and lockfiles — none of those are meaningful to compare.

## Environment setup

- Node `>=22`.
- Package managers: npm ships with Node; yarn/pnpm may need `corepack enable`; bun may need a separate install (e.g. `brew install bun`). Test all four — package-manager-specific bugs have shipped before (pnpm's build-script approval policy, bun's lockfile naming).
- pnpm ≥10 blocks postinstall/build scripts by default (`ERR_PNPM_IGNORED_BUILDS`). The CLI is expected to auto-recover from this (`pnpm approve-builds --all`) — if you're specifically testing that recovery path, seeing the initial block-then-recover in the logs is expected, not a failure.
- In tightly sandboxed CI/agent environments, a child process binding a listening TCP port (`dev`, `serve`/`serve:only`) may itself be killed by the sandbox before it can be smoke-tested with a real HTTP request. If that happens in your environment, fall back to `node --check` on the relevant entry file plus the `build`/`build:prod` coverage you already have — that isn't a nutin bug, it's an environment constraint.

## Workspace

Generate every scratch app outside this repository (a temp directory, or an untracked directory covered by `.gitignore`) — never inside `packages/nutin` itself. Each matrix cell in `MATRIX.md` is one scratch app (or one mutation of an existing scratch app, where noted).

## Execution order

Run the dimensions in `MATRIX.md` in order, A through E. Later dimensions can reuse apps generated by earlier ones where the matrix says so, to cut down on redundant installs — e.g. Dimension B reuses Dimension A's full-preset apps rather than regenerating them.

## Definition of done

Every cell logs pass/fail with captured stderr on failure. Every item in `MATRIX.md`'s regression checklist reconfirmed empirically against a real build — not by reading the template that once had the bug and assuming it still doesn't.

## Reporting

This folder documents the *test design*, not any specific run's results — don't add a results/report file here, since that would go stale the moment the CLI changes again. Record findings from an actual run wherever this project already tracks changes/issues (e.g. a `CHANGELOG.md` entry for a fix, an issue for something left open) so this matrix stays reusable for the next person/agent who runs it.
